# AVX-vectorized GEMM — deductive verification (Frama-C/WP + Coq)

Формальная верификация умножения матриц `C = A * B`, реализованного на
AVX-интринсиках, средствами Frama-C/WP. Цели, недоступные SMT-решателям,
закрыты интерактивными доказательствами в Coq (`coq_prove/`).

## Что доказано

```c
/*@
  requires \valid_read(A + (0 .. M*K-1));
  requires \valid_read(B + (0 .. K*N-1));
  requires \valid(C + (0 .. M*N-1));
  requires \separated(A + (0 .. M*K-1), C + (0 .. M*N-1));
  requires \separated(B + (0 .. K*N-1), C + (0 .. M*N-1));
  requires M > 0 && N > 0 && K > 0;
  requires N % 16 == 0;
  ensures MatrixResult{Post}(A, B, C, M, K, N, M);
*/
void gemm_v2(int M, int N, int K, const float *A, const float *B, float *C);
```

Постусловие разворачивается в полное определение матричного произведения:

```
MatrixResult{Post}(A,B,C,M,K,N,M)
  → ∀ i<M:      RowResult{Post}(A,B,C,N,i,K,N)
  → ∀ i<M, j<N: DotProduction(A,B,K,i,K,j,N, C[i*N+j])
  → ∀ i<M, j<N: C[i*N+j] = Σ_{k<K} A[i*K+k] · B[k*N+j]
```

`DotProduction` функционален: два его случая имеют непересекающиеся охранники
(`0 >= to` и `0 < to`), а шаг детерминирован, поэтому предикат фиксирует для
каждой ячейки `C` ровно одно значение. Спецификация не может быть удовлетворена
«чем угодно».

Порядок накопления в предикате (`res + A[...]·B[...]`, слева направо по `k`)
совпадает с порядком в коде.

## Спецификация

Аксиоматика `MatrixMult` (в `gemmv2.c`) описывает результат тремя индуктивными
предикатами, по одному на уровень вложенности циклов:

| предикат | смысл |
|---|---|
| `DotProduction(A,B,to,i,K,j,N,res)` | `res` — частичная сумма по первым `to` слагаемым для ячейки `(i,j)` |
| `RowResult{L}(A,B,C,to,i,K,N)` | первые `to` колонок строки `i` посчитаны полностью |
| `MatrixResult{L}(A,B,C,to,K,N,M)` | первые `to` строк посчитаны полностью |

Вспомогательные леммы:

- `math_bounds`, `mul_mono_nonneg`, `div8` — нелинейная арифметика индексов;
- `dp_frame`, `row_frame`, `mat_frame` — перенос факта между двумя метками,
  когда задействованные диапазоны `A`/`B`/`C` между ними не менялись;
- `fmadd8_step` — закрывает все 8 колонок одного блока `fmadd`+`store`
  разом: «если 8 колонок были верны на шаге `to-1`, а `C` обновили по формуле
  `av*B + C_old`, то все 8 верны на шаге `to`».

Последняя нужна, чтобы внутренний цикл описывался двумя `assert`-ами
(`block0`, `block1`) вместо отдельного ассерта на каждую колонку.

## Модель регистра `__m256`

```c
typedef struct { float e[8]; } __mm256;
```

Регистр моделируется как **значение**, а не как адрес в памяти — так же, как
он устроен физически. Следствия:

- между двумя `__mm256` по определению не может быть алиасинга, поэтому
  никаких `\separated` между регистрами не требуется;
- все интринсики, возвращающие регистр (`_mm256_setzero_ps`, `_mm256_set1_ps`,
  `_mm256_loadu_ps`, `_mm256_fmadd_ps`), имеют `assigns \nothing`;
- `\valid` / `\valid_read` / `\separated` остаются только там, где реально
  происходит обращение к памяти — в `_mm256_loadu_ps` и `_mm256_storeu_ps`.

Си-код никогда не разыменовывает `__mm256` через `[]` — индексация `x.e[i]`
встречается только внутри ACSL-формул.

Используются невыровненные варианты `loadu`/`storeu`: в этой версии WP
предикат `\aligned` не поддерживается, так что выровненные `load_ps`/`store_ps`
пришлось бы специфицировать нечестно.

## Структура кода

Порядок циклов `i`–`k`–`j`: `B` и `C` читаются со stride 1 вдоль `j`, элемент
`A` рассылается по всем лейнам через `_mm256_set1_ps`.

```
for i in 0..M:                    // MatrixResult{Here}(A,B,C,i,K,N,M)
    for j in 0..N step 8:         // обнуление строки, zeroed{Here}
    for k in 0..K:                // ∀l: DotProduction(A,B,k,i,K,l,N,c[l])
        for j in 0..N step 16:    // два блока fmadd+store → block0 / block1
```

Частичные суммы живут в памяти (`c[j]` перечитывается на каждой итерации `k`),
а не в регистрах. Это осознанный выбор: инвариант внутреннего цикла остаётся
формулой о содержимом `C`, а не о содержимом регистрового тайла.

## Как прогнать

```bash
frama-c -wp -wp-rte gemmv2.c
```

Coq-цели в `coq_prove/` сгенерированы и доказаны для вещественной модели
арифметики:

```bash
frama-c -wp -wp-model "Typed+nat+real" -wp-prop="<цель>" \
        -wp-prover coq -wp-interactive update gemmv2.c
```

Модель здесь существенна: под моделью IEEE-754 WP порождает другую Coq-кодировку
(`Mf32 : addr -> t`, значения через `t'real(...)`) с другим набором и порядком
гипотез, и готовые доказательства к ней не подходят.

## Границы применимости

- Арифметика вещественная, не плавающая: доказано, что алгоритм вычисляет
  произведение матриц в точной арифметике. Ошибки округления, чувствительность
  к порядку суммирования и поведение на NaN/Inf вне охвата. Контракт
  `_mm256_fmadd_ps` (`a*b + c`) корректен именно в этой модели — настоящая
  инструкция FMA округляет один раз, а не два.
- `N % 16 == 0` обязательно: хвостовых итераций в коде нет.
- Индексные выражения (`i*N`, `i*K`, `k*N`) вычисляются в `int`; отсутствие
  знакового переполнения для больших матриц отдельно не доказывается.

## Обоснование выбора модели регистра

Перед тем как остановиться на struct-значении, были рассмотрены альтернативы:

- [ACSL malloc-контракт (`\fresh`/`allocates`)](https://github.com/acsl-language/acsl/blob/master/malloc-free2-fn.c) —
  стандартный ACSL-паттерн для функции, возвращающей заведомо свежий,
  ни с чем не пересекающийся блок памяти (`ensures \fresh(\result, n)`).
  Выглядит подходящим для «регистр = свежевыделенный блок», но:
- [Frama-C-discuss: регионы WP для malloc-аксиоматики](https://frama-c.com/html/fc-discuss/2017-March/msg00003.html) —
  WP не поддерживает `\fresh`/`allocates` нативно и не выводит из них
  разделение памяти автоматически; потребовалась бы ручная аксиоматика через
  внутренние «регионы» WP. То же подтверждает `notes/frama-c-wp-manual.pdf`
  (раздел 1.6 Limitations & Roadmap: *«Dynamic allocation... ACSL clauses for
  specifying allocation and deallocation are not implemented yet»*).
  Для используемой версии WP путь тупиковый.
- [HACLxN: Verified Generic SIMD Crypto](https://project-everest.github.io/assets/haclxn.pdf) и
  [EverCrypt: A Fast, Verified, Cross-Platform Cryptographic Provider](https://www.researchgate.net/publication/343340372_EverCrypt_A_Fast_Verified_Cross-Platform_Cryptographic_Provider) —
  в верифицированном SIMD-крипто-коде (Vale/Jasmin в HACL*/EverCrypt) регистр
  моделируется как **значение** в состоянии абстрактной машины, а не как адрес
  в куче. Это устоявшийся паттерн моделирования SIMD-регистров в deductive
  verification, а не технический трюк.
